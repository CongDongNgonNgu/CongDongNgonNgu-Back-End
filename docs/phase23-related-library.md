# Reviewed related-resource Library implementation

Phase23 bounded Backend slice; canonical Workspace `RELATION-CONTRACT.md` remains the policy authority. No benchmark edges or collection membership rows become assertions automatically. No relations are seeded.

`GET /api/v1/library/resources/:resourceId/related` accepts only `relation`, `language`, `type`, `level`, `cursor`, `limit`. Default3/max12. Output is `{items:[{resource:<canonical public Library resource>,relation:{type}}],nextCursor}`. Existing UUIDv4/error/success envelopes apply. Ineligible anchors use the same generic404 as detail; empty target sets are honest empty. Existing Library detail/search remain available.

Assertions are directed and explicitly reviewed through `LibraryRelationsService.review(reviewerUserId,{anchorId,targetId,type,evidenceReference})`; `revoke` accepts the same endpoint/type keys. These trusted internal methods have no public mutation route. Current trusted identity must be ACTIVE MODERATOR/ADMIN. Review records the current complete endpoint fingerprints, evidence reference, reviewer and timestamp; re-review/revoke advances revision. Eligibility, review authority, resource/source/license facts and assertion revision are checked again during final public projection. Changed facts require explicit re-review; reads never refresh assertion fingerprints.

Selection scans64target UUIDs ordered ascending, followed by accepted type order; one current-valid assertion per target survives. A separate SQL `EXISTS` continuation probe returns only a boolean after the64th boundary; it does not return/materialize a65th candidate UUID. The cursor contains authenticated-encrypted keyset state (AES256GCM/random nonce), with a domain-separated key derived from existing JWT access secret. Anchor, normalized filters and limit bind authenticated context. Key rotation, modification and mismatched queries fail400. There is no relation/browser/server cursor cache or recursion.

## Related-only capacity limitation

The explicit work budget is32provenance entries per resource. SQL checks a capped33-row count before hydration and again within the provenance read; memory checks before cloning. Oversized resources are omitted whole, with no partial citations or licenses. Canonical detail/search eligibility remains unchanged; an oversized anchor may be unavailable on this related endpoint even when ordinary detail is public. This is bounded safe abstention with lower recall, not a claim that the resource is canonically ineligible. Existing trusted content/schema limits still apply; no universal byte-size claim is made.

## Query cost and current-read guarantee

For the built-in PostgreSQL repositories, batch resource hydration uses1base query,2component queries (topics/provenance), plus1detail query for each represented resource type: `3+T`, at most13. Empty/entirely oversized batches stop after the base read. Current license registry is read in1batch query per projection pass. Coherent Phase06 source references use1deliberate batch health query per projection pass; malformed references fail closed. Non-Phase06 sources retain NOT_APPLICABLE. Review authority uses1batch identity query per selection/final pass.

Three projection passes read the anchor, up to64candidate targets, then anchor plus up to12prepared targets. Each resource has at most32provenance entries; the candidate pass therefore inspects at most2048entries. Relation scan needs1identity query,1assertion batch and, when64identities were returned,1boolean continuation probe. Final assertion re-read is1batch. Worst-case round-trip bound is43SQL statements when a language filter requires current active-language validation (hydration30, licenses3, health3, assertion/continuation4, identity2, language1), or42 without that filter; no claim that all43 execute for every request. This is an implementation bound to verify with PostgreSQL query observations, not fabricated measured latency. Compatibility adapters that lack optional source/identity batch methods use bounded fallback reads; built-in PostgreSQL does use both batches.

The guarantee is eligibility re-evaluation at selection and final public projection. Ordinary separate reads do not establish atomic SQL revocation, distributed concurrency guarantees or post-response browser freshness. No provider/corpus/user usefulness or linguistic certification claim follows.
