# Disabled attachment cleanup composition

AttachmentCleanupWorker is an internal awake-only scheduler, not an enabled module or public route. start performs a boot kick and schedules every frozen60seconds; run/kick share one active run, stop prevents new claims and waits for the active bounded work. Metadata expiry/completion and physical jobs share one20candidate budget. Provider calls stay outside database transactions. Sleeping Free TEST hosts have no deletion deadline.

PostgresAttachmentCleanupRepository uses unlocked bounded candidate selection only; every mutation re-enters system account/domain/attachment/object/job order through AttachmentLifecycleLedger. Disabled or revoked owners cannot block internal retirement, and these operations never grant user reads. Physical cleanup requires an exact durable claim; uncertain PUTs are excluded and are never settled from negative HEAD or elapsed lease. Known snapshots use the storage adapter's fresh full ownership comparison before exact unconditional deletion; a never-started key must already be absent and is never blindly deleted. Independent exact-key HEAD and listing checks precede finish, whose internal post-probe receipt uses DB time. Lease/version/locator checks remain authoritative.

Completion retains byte/metadata reservation until all manifest objects are DELETED/settled, jobs complete and producer/processing ownership cleared. Metadata maintenance then releases the reservation exactly once under current system locks. Failure records only allowlisted codes with bounded backoff, retains debt and emits safe job-ID alerts. Ten acquired cleanup attempts exhaust ordinary retry eligibility; no ownership or reservation is discarded. Alerting failure does not change debt.

Tests with synthetic provider responses and real isolated SQL transactions establish orchestration, not actual deployed storage cleanup. No bucket-wide listing/deletion or backup namespace operations exist here. Unknown owned-prefix objects, uncertain producer reconciliation, retained-row/counter purging, actual boot/restart integration and exact Render cleanup acceptance remain separate unfinished gates. This source alone does not claim complete orphan reconciliation or a live cleanup service.
